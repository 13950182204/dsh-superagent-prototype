---
name: dsh-superagent-gitlab
description: Read GitLab issues, merge requests, notes and pipelines using glab.
---

Workers use orchestrator_read for project context when needed: gitlab/issues/<iid> or gitlab/merge_requests/<iid> for the description; gitlab/issues/<iid>/notes/1 and gitlab/merge_requests/<iid>/notes/1 for conversation notes; gitlab/merge_requests/<iid>/discussions/1 for the discussion threads; gitlab/merge_requests/<iid>/thread/<discussion-id> for one discussion, including its inline diff note; gitlab/merge_requests/<iid>/pipelines and gitlab/commits/<sha>/pipelines for CI. A page holds 20 entries and names next_resource while another may follow. A note is `{ id, from, at, text, reply_to?, path?, line?, url }`: `id` is GitLab's note id, `reply_to` the URL of its thread's first note, `path` and `line` an inline note's file and line, and `bot: true` marks a bot, whose words never authorize work. Continue with next_resource when a response names one; page numbers read further pages of the same conversation. Reading does not create tickets or send replies. System notes, such as label changes and pushes, are activity rather than messages and never arrive. Allowed mentions subscribe the issue or merge request, and later notes on a subscribed Thread arrive without another mention; merge requests opened from the ticket's branch are followed. Issue 5 and merge request !5 are separate Threads, so answer where the request was made. Other activity is available on demand; read the CLI instructions included in this skill for glab access to context beyond these shortcuts.

Before substantial work on a new human request or note, call `orchestrator_ack` with its original trigger ID and a brief request-specific `text`, even within an existing ticket; the host replies once in that source thread. This acknowledgement is separate from how diff discussions are answered. Do not acknowledge bots or CI.

Reply with `glab api` through the wrapper, run from the ticket checkout so `glab` reads the project and its server; a reply is a note. On an Issue, `glab api "projects/<encoded>/issues/<iid>/notes" --method POST -f body=<text>`; on a merge request, `glab api "projects/<encoded>/merge_requests/<iid>/notes" --method POST -f body=<text>`; for an inline diff note, answer inside its discussion with `glab api "projects/<encoded>/merge_requests/<iid>/discussions/<discussion-id>/notes" --method POST -f body=<text>`, so the answer stays attached to the diff line. `<encoded>` is `$DSH_SUPERAGENT_GITLAB_PROJECT` from the execution environment section with its `/` written as `%2F`. Do not post a plain merge request comment in place of a diff discussion reply. Read a merge request with `glab mr view <iid>` or `glab api "projects/<encoded>/merge_requests/<iid>"`; its `merge_status`, `has_conflicts` and `head_pipeline` say whether it can merge. Record the bot run identifier, review-round count and dispositions in `orchestrator_report`; the merge request description retains the final implementation, verification and material limitations.

Merge only with `glab mr merge <iid> --yes` from the ticket checkout, and only after the ticket's delivery policy allows it; the plugin never merges a GitLab merge request for you. GitLab 13.1 Community Edition has no approvals API and no server-side auto-merge, so there is no approval to wait for and no auto-merge to enable. Merge only when the merge request is open, free of conflicts, and its pipeline passed, was skipped, or has not run.

Never force-push, never bypass or change the project's protected branches, never merge a merge request the ticket did not open, never touch the wrapper's token or configuration directory, and never use a personal `glab` configuration. Immediately after creating or adopting a ticket merge request, call `orchestrator_report` with `state: progress` and the merge request number in `pr_number`; do not wait for CI or handoff. Read each original trigger and acknowledge new human requests before substantial work. Worker reports still go to the orchestrator for concise source-conversation delivery.

Where the Delivery requirements or work instructions name `gh`, a `gh pr …` command, `$DSH_SUPERAGENT_GITHUB_REPOSITORY`, `$DSH_SUPERAGENT_GITHUB_ACCOUNT` or `$DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL`, read them as `glab`, `glab mr …`, `$DSH_SUPERAGENT_GITLAB_PROJECT`, `$DSH_SUPERAGENT_GITLAB_ACCOUNT` and `$DSH_SUPERAGENT_GITLAB_COMMIT_EMAIL`; a pull request is a merge request and an issue is an Issue. The merge CLI is `glab mr merge <iid> --yes`, and GitLab 13.1 Community Edition has neither approvals nor auto-merge, so a person merges every merge request unless the Delivery requirements say otherwise.
